# LZ77 接收端帧率优化（2026-10-25）

本次只改用户态软件，沿用已验证的 v32 bit、内核驱动、4 KiB DMA read、BLK1 协议及完整 CRC。
当前用户确认的基线：RAW 带框显示约 60 FPS、YOLO 20～30 FPS，开启 LZ77 视频约 15～20 FPS。
MP4 往返约 6 FPS 是另一条处理链路，不与实时摄像头播放 FPS 混用。
本次优化的实际板端增益尚未测量，不宣称 LZ77 已达到 30 或 60 FPS。

## 改动与边界

- BLK1 的重复匹配不再逐字节展开。distance=1 使用 memset，不重叠匹配用 memcpy，
  重叠匹配先复制种子、再分段倍增。仍严格检查块内距离、输出长度、token 数和整帧 CRC；
  旧协议共用相同解码函数。原始回退块本来已经使用 memcpy，本次不改变其像素或压缩率。
- RGB24 stdout 为 FIFO/pipe 时尝试将管道扩大到 1 MiB，减少频繁的读写交接。
  不缩小现有管道，权限或资源不足时保留原容量继续工作；日志 PIPE_OUTPUT 记录实际值。
  这是有界字节缓冲，可能增加少量排队延迟，并非零拷贝，也不会通过重复或丢弃接收帧提高 FPS。
- 增加 assemble_ms、output_wait_ms，分别统计累加器扩容/拷贝与帧边界解析、等待可用输出槽。
  assemble_ms 不含 CRC 和解码，不包括所有主线程指令，不能当作完整 parser CPU 占用。
- PERF_DMA 每次采样记录 DMA 实际返回字节、调用次数、排除首次读取后的平均 read 耗时、
  输入环满累计等待秒数、当前/峰值槽数和采样间隔吞吐。首次 interval_MBps=0，表示尚无前次采样。
  read 耗时包含内核调度、FPGA 等待和传输，不等于 PCIe 硬件传输延迟；负载终止前在途读取未计入。
- 保留 RX_MATCH_COPY=scalar、RX_PIPE_BYTES=0 作为诊断对照，默认 fast 和 1048576。
  scalar 是逐字节参考实现，不是切换回旧二进制；尤其旧 legacy 协议本来就有部分快速路径。
- 不更改 FPGA、驱动、相机帧率或 YOLO stats/KMS 默认行为，不增大未经完整性验证的 DMA 请求。

## 已完成本地检查

完整接收源码通过 aarch64-linux-musl 与 aarch64-linux-gnu 的 C11 编译检查（-O2 -Wall -Wextra -Werror）。
其中 ARM Linux 编译包含硬件 IEEE CRC32 路径；最终仍需板端 GCC 和运行验证。

Windows 本地从实际源码提取的可移植 C 解码核心已验证：255 种距离×125 种长度、
重叠与不重叠复制、BLK1/legacy、多块字典隔离、1080p 原始回退/高重复/混合图像、
碎片帧边界、完整像素、错误距离拒绝、CRC 错误拒绝及 table/slice8 CRC 自测。
高重复 1080p 样本本地解码整体约由 6.9 ms 降至 1.8 ms；该数字来自 Windows x86_64，
包含该测试的 CRC、分配和输出拷贝，不是 RK3576 数据，也不代表实时链路 FPS。
原始回退样本没有显示明显收益，若场景几乎全为 raw block，主要瓶颈仍需用板测区分。
Shell 语法检查通过。DMA、pthread 停止/排空、管道容量调整和 GStreamer 显示尚待本轮板测。

## 上板步骤（只需一个窗口）

先在电脑 Xftp 中，把最新版 deploy 内容合并到开发板 `/home/linaro/deploy`，
包括新的 rk3576 源码、脚本和 SHA256SUMS；不要复制成 `/home/linaro/deploy/deploy`。
保留板端匹配当前内核的驱动 .ko 和模型，停止网页启动的旧播放器后再更新和测试。

在连接开发板的 **PuTTY 窗口**执行下面命令（提示符应是 root@linaro-alip）：

```bash
cd /home/linaro/deploy
sha256sum -c SHA256SUMS && (
  set -e
  cd rk3576
  bash build.sh
  ./rk3576_lz77_rx --optimization-info
  ./rk3576_lz77_rx --self-test-crc
  python3 test_lz77_blocks.py --receiver ./rk3576_lz77_rx
  python3 test_lz77_match_copy.py --receiver ./rk3576_lz77_rx
  python3 test_receiver_pipeline.py --receiver ./rk3576_lz77_rx
)
```

如果以 linaro 登录，先执行 `sudo -i` 切换到 root。任何检查失败就停止，保留完整输出。
优化标识应为 `rx-blk1-match-pipe-20261025`，旧 --version / --build-info 保持兼容值。
不需要重新烧录 FPGA 或重载驱动。

以上全部 PASS 后，在**同一个 PuTTY 窗口**执行：

```bash
cd /home/linaro/deploy
set -o pipefail
bash benchmark_lz77_fps.sh 8 188 35 2>&1 | tee /home/linaro/lz77-fps-20261025.log
```

脚本依次运行 headless_scalar、headless_fast、display_scalar、display_fast，各 35 秒。
headless 两轮不显示视频是正常行为。保持镜头、光照不变，勿同时启动网页播放或其他采集程序。
结束打印 `/tmp/pcie-video-report.*.zip`，从 Xftp 下载该 ZIP 和控制台日志即可，不需第二个窗口。
mode 8 通过后，可将第一个参数改为 9 复测。

需要增加一轮带框 stats 测试时，在上述 benchmark 命令前加：
`YOLO_MODEL=/home/linaro/deploy/yolo/yolov5s_relu.rknn YOLO_KMS_OVERLAY=1`。
仅使用 stats，不自动执行 boxes/boxes-sync。检测帧率单独从同轮 YOLO 日志读取。

## 如何决定下一步

先检查 CRC/decode/format、硬件帧错误均为 0，再比较稳定区间的 interval_fps 和 DISPLAY FPS，
不以包括启动等待的短测试平均值或显示刷新率代替成功接收帧率。

- 如果 decode_ms 下降、整体 FPS 不变，说明解码已变快但不是主要限制。
- 如果 output_wait_ms/环满等待显著、display 比 headless 慢，继续调查显示背压与 RGB24 输出。
- 如果 headless 与 display 接近、环满等待接近零且 read_wait_ms 很大，优先分析 FPGA 供数和 DMA。
  必须结合 hardware.log 的 comp_frames/DDR_NO_SLOT 与驱动阶段统计，不能仅凭 read_wait 断定驱动故障。
- 原图几乎全为 raw block 时，1080p RGB24 的 30 FPS 需约 186.7 MB/s 线速数据，
  60 FPS 需约 373.3 MB/s。实际吞吐必须由全链路测量，CRC 与驱动提交开销仍需保留。
