# v27：PH1A MIPI 延时路径与扫描修正

用户 source.IiS0tE 测试没有 DMA 消费者；enable=1、camera_per_s 持续为 0，
完整打包计数为 0。各级曾见帧/行标志为 0xff，门控只记录一次帧起点。
这说明各级曾发生事件，未证明它们能持续形成完整帧。源端失败时不应继续
将 DMA 带宽当作首要定位目标。

## 找到并修正的代码问题

1. **PH1A 延时使能误接加载脉冲。**
   csi_rx_hs_data_phy.v 原来将 PH1_LOGIC_DYNAMIC_IDELAY.indly_en 接到
   I_delay_vaild。TD 厂商模型的输出为 `indly_en ? delayed : input`；
   扫描脉冲后就回到旁路。本次改为连续使能，并在 byte clock 上锁存
   五位档位代码。代码更新只发生在加载脉冲，复位选物理中点 16。
   PH2 的 dl_en_n 加载接口保持原行为，不套用 PH1A 的使能语义。
2. **扫描范围与物理范围不一致。**
   PH1A primitive WIDTH=5，只接受 0…31。旧扫描 0…63，会截断并重复
   扫同一物理档位。本次从 csi_rx_phy 给扫描器传 DELAY_TAPS=32；
   PH2 默认 64 档。无窗口时使用各自范围的中点。
3. **64 档全通过的长度溢出。**
   cur_len/best_len 从六位扩为七位；中心计算使用完整长度。
   原六位调试接口保留：PH1A 最大真实报告 32，其他 64 档全通过报告 63
   （饱和），不会错误报告 0。

所以此前对 best_len=0 的解释需要修正：旧版可能是没有窗口，也可能是
六位长度溢出；而其 tap 脉冲连接还会使扫描观察不到持续生效的延时。
目前修正的是明确的代码缺陷，不是已经实测确认这些缺陷解释了全部板上现象。

## 回归

`uisrc/02_sim/mipi_scan/run_scan.ps1`：

- 32、64 档：无窗口、窄窗口、间歇对齐、多个窗口、最末档、全窗口。
  校验精确中心、真实长度、唯一且合法的扫描档位、最终值稳定。
- PH1A 数据路径使用 TD 的真实 IDELAY 仿真模型；仅 IDDRx2 为接口 stub。
  脉冲结束后仍保留上升/下降边沿延时、未加载不改变档位、复位恢复中点。
  ModelSim 编译及这两组测试均通过，Errors=0、Warnings=0。
- 同一延时测试应用到改动前源码，复现 `Rising delay 0 ps, expected 630 ps`
  的 Fatal：证明原连接在加载后旁路。见 legacy_delay_reproduction.log。

这不是真实 D-PHY 眼图、板级时钟或传感器流的仿真验证；还需要上板 source
观察和完整帧测试。扫描指标仍沿用 byte alignment，未新增包 CRC 质量评分。

## 版本及构建

原工程参数版本改为 0x56440027，deploy 的验证、监测、播放、完整性测试
允许相同寄存器映射的 v27。接收程序与驱动本次不修改。
原源码与 17:01 候选 bit/布线数据库保存在
`imx415_pcie_4k_Runs/before_mipi_scan_fix_20261014`；test2 v26 独立回退不修改。

新综合、布局布线已在原工程 syn_1/phy_1 完成。最终 routed、fast/slow 双角：
setup WNS **+0.412 ns**、TNS=0；hold WNS **+0.020 ns**、TNS=0；
两者违例端点为 0。STA coverage 99.48%。检查项仍有 no-clock 6、dummy 类别 5、
PLL/clock 2、no-input-delay 33、no-output-delay 55、abnormal-input-delay 3；
invalid constraint、组合环和 ignored/shadowed exception 均为 0。
这代表已约束、已分析路径通过，不是所有外部接口及 CDC 已完成签核。
旧 +0.075/+0.020 ns 报告属于此前 v26 候选。

最终物理资源：LUT6 30131/64320（46.85%），FF 40716/128640（31.65%），
Slice 37921/64320（58.96%），ERAM195/272（71.69%），DSP62/240（25.83%）。
PCIe USR-6144 属于另外的动态时钟告警，本次修改不能被描述为消除了该告警。

## 新位流上板后的顺序

确认读回 0x56440027；复制更新 deploy 脚本；先 source 观察约 12 秒。
若 source 持续接近 60 FPS，再运行 raw 采集；若仍为 0，继续查 MIPI 有效包、
RAW10 行场尺寸、ISP/打包帧边界，不能只根据 sticky=0xff 判定前级通过。
source 不读 DMA，下游 FIFO 填满和 gate drops 可增长，不用于完整性验收。
